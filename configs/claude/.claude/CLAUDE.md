# Language

Always respond in Japanese (日本語), regardless of the language the user writes in.

# Git

- 変更したら `git add` でステージし、コミットせずに止める
- `git diff --staged` で変更を利用者に確認してもらい、承認をもらってからコミットする
- 変更単位で要約とコミットメッセージ案を添える
- コミット直前に `git status` を見せ、未ステージの変更があれば含めるか確認する。黙って巻き込まない。
- レビュー中に利用者がファイルを修正することがある。ディスク上の変更は意図的なものと
  して扱い、勝手に戻さない。壊れている場合だけ指摘する。
- 担当はコミットまで。`git push` は指示された場合も実行しない。push は利用者の作業とする。

## Commit Messages

プロジェクトで規約が明文化されていればそれに従い、なければ以下で書く。

- Conventional Commits に準拠し、scope は付けない
- 件名は英語、本文は日本語で書く
- type の後の説明は小文字で始めて命令形で書き、末尾にピリオドを付けない

### 件名

- 件名は開発者向けの変更履歴の1項目として書き、
  `git log --oneline` で各変更の意味が分かるようにする
- 機能変更は何を追加・変更・削除したか、不具合修正はどの症状を直したか、
  内部変更は何を整理・改善したかを書く
- fix の件名には、どう直したかではなく、修正した症状を書く。
  特定の条件で起こる症状は、その条件も含める
- 内部変更では、構造や実装の変更そのものを説明してよい
- ファイル名や作業内容を列挙するだけの説明、
  「改善する」「整理する」だけで対象や内容が分からない説明は避ける

### type

- type はコミット全体の目的に対して付ける。
  変更したファイルの種類や実装手段だけでは決めない
- 以下を上から判定し、最初に当てはまったものを使う
  1. fix: 想定する使い方で、仕様や期待する動作を満たさない問題を直した。
     未報告・未発生でも、具体的な条件で起こり得る不具合を含む
  2. feat: 不具合修正以外で、製品の機能・振る舞い・見た目を追加・変更・削除した
  3. docs: ドキュメントやコメントだけを変えた
  4. refactor: 製品の振る舞いを変えずに、コードの構造や保守性を改善した
  5. chore: それ以外（依存更新、テスト、CI、ビルドなど）
- 現在のコードで起こり得る不具合の修正は fix、
  将来の変更で不具合を生みやすい構造の改善は refactor とする
- 依存更新などでも、製品の不具合修正や機能変更が目的なら fix / feat を優先する
- 公開 API やサポートしている使い方の互換性を壊す変更は、
  type にかかわらず直後に `!` を付ける

### 本文

- 本文は件名だけで伝わらない情報があるときだけ書く
- 何が問題だったか、なぜ変更が必要だったか、なぜこの方法を選んだかを中心に書く。
  件名や差分から明らかな内容は繰り返さない
- 互換性を壊す変更では、件名で伝えきれない非互換の内容を本文に書く。
  移行手順が必要なら、それも書く

### コミットの単位と判断に迷ったとき

- 1コミット1つの論理的な変更にし、その変更を後から取り消す単位としてまとめる
- 実装と、それに依存するテスト・ドキュメントは同じコミットに含める
- 変更を取り消しても単独で成立し、残す意味があるテストの追加や
  リファクタリングなどは、別コミットにする
- 別々に取り消す可能性がある独立した変更は、コミットを分ける
- 件名を付けにくい場合は、変更の目的が明確か、
  独立した変更が混ざっていないかを先に確認する
- type に迷ったら、変更の目的と影響に基づいて判断する。
  判断に必要な仕様や期待する動作が不明なら確認する
- 既存の分類では適切に表現できない変更は、無理に当てはめず、
  理由を示して type の追加・変更などを提案する

# Proposals and Opinions

提案や意見を述べるときは、ユーザーがどう思っていそうかを考慮に入れず、あなた自身が最善だと思うことをそのまま伝えること。

理由: ユーザーは自分の考えに引っ張られて視野が狭まることを避けたいと考えている。

具体的には:
- ユーザーの意向に沿うように結論を調整しない
- ユーザーが既に選んだ案でも、より良いと思う案があれば率直に提示する
- 遠慮して選択肢を並べるだけにせず、「私はこれが良いと思う」と立場を明確にする
- ただし確信がないことは「未確認」「推測」とはっきり言う。
  不確かさの表明は遠慮ではなく正確さなので、これは省略しない
