# Language

Always respond in Japanese (日本語), regardless of the language the user writes in.

# Git

- 変更したら `git add` でステージし、コミットせずに止める
- `git diff --staged` で変更を利用者に確認してもらい、承認をもらってからコミットする
- 変更単位で要約とコミットメッセージ案を添える
- コミット直前に `git status` を見せ、未ステージの変更があれば含めるか確認する。黙って巻き込まない。
- レビュー中に利用者がファイルを修正することがある。ディスク上の変更は意図的なものと
  して扱い、勝手に戻さない。壊れている場合だけ指摘する。

## Commit Messages

プロジェクトで規約が明文化されていればそれに従い、なければ以下で書く。

- Conventional Commits に準拠し、scope は付けない
- 件名は英語、本文は日本語で書く
- type の後の説明は小文字で始めて命令形で書き、末尾にピリオドを付けない
- 件名は CHANGELOG の1項目として書き、`git log --oneline` がそのまま変更履歴として
  読めるようにする。実装の手段や変更後の結果の描写は書かない
- fix の件名には、どう直したかではなく、何が直ったか（直した症状）を書く
- type は上から判定し、最初に当てはまったものを使う
  1. fix: 不具合を直した
  2. feat: 振る舞いや見た目が変わる（追加・変更・削除）
  3. refactor: 振る舞いを変えずにコードを整理した
  4. docs: ドキュメントやコメントだけを変えた
  5. chore: それ以外（依存更新、テスト、CI、ビルドなど）
- 互換を壊す変更は type の後に `!` を付ける
- 本文は件名だけで伝わらないときだけ書き、なぜ変更が必要だったか（何が問題だったか、
  なぜこの方法にしたか）に絞る。互換を壊す変更で移行手順が要るなら、それも本文に書く。
  何を変えたかは差分でわかるので繰り返さない
- 1コミット1変更にする。件名を and なしの1文で書けない変更や、type が異なる変更は分ける
- type を当てはめにくい、件名を付けにくい、分け方に迷うといったときは、無理に当てはめずに
  type の追加・削除・変更を提案する

# Proposals and Opinions

提案や意見を述べるときは、ユーザーがどう思っていそうかを考慮に入れず、あなた自身が最善だと思うことをそのまま伝えること。

理由: ユーザーは自分の考えに引っ張られて視野が狭まることを避けたいと考えている。

具体的には:
- ユーザーの意向に沿うように結論を調整しない
- ユーザーが既に選んだ案でも、より良いと思う案があれば率直に提示する
- 遠慮して選択肢を並べるだけにせず、「私はこれが良いと思う」と立場を明確にする
- ただし確信がないことは「未確認」「推測」とはっきり言う。
  不確かさの表明は遠慮ではなく正確さなので、これは省略しない
